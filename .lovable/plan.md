## Problem

A player who pays an invoice and then tries to download the PDF gets a generic "something went wrong" error. There are two surfaces involved, and both have issues:

1. **Public invoice page** (`/pay/:token`) — after Mollie payment succeeds, the page shows a green checkmark but **has no download button at all**. The only path forward is "create an account / go to my account", which is a dead end for guests who don't sign up. If they had a link from email, clicking it again returns `already_paid` (the public token is intentionally revoked once paid, per the public-invoice-privacy memory rule), so there is no working download path through the public token.

2. **Authenticated player tab** (`/app/player` → Invoices) — calls `generate-invoice` via `downloadInvoicePdf`. The auth check accepts `invoice.player_id` linked to the signed-in user. But for invoices created against a guest (`player_id = null`, `guest_player_id` set), the link only happens after the `link_guest_invoices_on_signup` trigger runs (matched by email). If the player signed up with a different email than the guest record, `player_id` stays NULL and the download returns 403 → toast `pdfError` ("Could not generate invoice").

## Fix

### 1. Add a download path on the public paid screen

- Extend `get-public-invoice` so that when an invoice is already paid, instead of just returning `{ error: "already_paid" }`, it ALSO returns a short-lived signed PDF URL for the invoice (generated by calling `generate-invoice` with the service role, same pattern as `get-booking-invoice`). This keeps the public token usable for the strict purpose of downloading the receipt without exposing PII back to the page.
- Update `PublicInvoicePay.tsx`: in the `isPaid` branch, render a "Download invoice" button that triggers a file download from that signed URL. Wire loading/error toasts.
- Add new i18n keys under `common` → `invoice`: `downloadInvoice`, `downloadingInvoice`, `invoicePending`, `invoiceFailed` (mirroring the existing player keys), translated for all 6 locales (en, nl, de, fr, es, it).

### 2. Allow generate-invoice to authorize via guest email match

In `supabase/functions/generate-invoice/index.ts`, extend the `!isServiceRole` authorization block:

- If the invoice has `guest_player_id` and the authed user's email (from `auth.users`) matches the guest's email, treat them as the player. This closes the gap for players who pay as a guest and later sign up — they can download their own invoices even before the link trigger runs (or if it failed).

### 3. Tighten client error reporting (small)

`src/lib/downloadInvoicePdf.ts` currently returns `false` on any failure and the toast just says "Could not generate invoice". Add a `console.error` with the actual `error.message` from the edge function response so future cases surface in console logs. No UX change.

## Out of scope

- Booking-flow download (`BookingSuccess` + `get-booking-invoice`) — already works and uses service role; not touching unless the user confirms the error appears there.
- Email-based PDF attachment — separate request.

## Files

- `supabase/functions/get-public-invoice/index.ts` (extend paid branch with signed PDF URL)
- `supabase/functions/generate-invoice/index.ts` (guest-email auth path)
- `src/pages/PublicInvoicePay.tsx` (download button on paid screen)
- `src/lib/downloadInvoicePdf.ts` (better error logging)
- `src/i18n/locales/{en,nl,de,fr,es,it}/common.json` (download strings under `invoice.*`)
